# 선택형 질문과 대화 유지

질문은 사용자가 가진 사실·선호 중 답에 따라 후보나 추천이 바뀌는 항목을 확인한다. 이미 프로젝트 자료나 대화에 있는 내용을 다시 묻지 않는다. 초기에는 조사에 꼭 필요한 것만 묻고, 나머지는 조사 요약을 설명한 뒤 묻는다.

## 도구 선택

- 현재 런타임에서 허용되는 구조화된 사용자 질문 도구를 우선 사용한다. Codex에서 `request_user_input_async`가 사용 가능하면 질문과 선택지를 해당 도구로 전달한다. 일반 답변에 질문만 적고 턴을 끝내는 방식을 기본으로 삼지 않는다.
- 동기 `request_user_input`은 현재 모드와 도구 계약이 허용할 때만 사용한다. Plan 모드 전용 도구를 쓰기 위해 사용자의 작업 모드를 임의로 바꾸지 않는다.
- 비동기 질문은 답변 전까지 미해결로 유지한다. 답과 무관한 근거 조사는 진행하고, 답에 의존하는 선택·기록은 기다린다. 필요한 경우 런타임의 대기 기능을 사용한다. 같은 질문을 다시 보내지 않는다. 시간 경과나 도구의 accepted 응답은 사용자 답변이 아니다.
- 구조화된 도구가 없거나 허용되지 않을 때만 번호 선택과 직접 입력을 본문에 제공한다. 이 대체 방식에서는 다음 답변을 기다리며, 클릭 가능한 UI라고 주장하지 않는다.

## 질문 구성

한 번에 1~2개 질문을 기본으로 한다. 선택지는 서로 구별되는 2~3개를 우선하고 각 선택의 판단 영향을 짧게 설명한다. 도구가 직접 입력을 기본 제공하면 `기타/직접 입력`이라는 중복 선택지를 추가하지 않는다. 제공하지 않으면 직접 입력할 수 있는 방법을 명시한다. 불확실한 사실에는 `아직 모름`을 허용한다.

예산·트래픽·배포 환경 등 사실 질문은 특정 사실을 권장하지 않는다. 도구의 기본 선택이나 필수 추천 표시는 사용자 사실을 확정하지 않으며, 실제 제출된 답만 반영한다. 필수 추천이 필요한 도구에서는 근거 없는 사실을 추천값으로 만들지 않도록 사용 가능한 다른 질문 도구나 자유 입력으로 전환한다. 선호 질문의 추천은 조사된 이유가 있을 때만 제시한다.

예시: “이번 선택에서 더 중요한 것은 무엇인가요?”

- 빠른 완성 — 기존 구성 재사용과 구현·운영 부담을 우선 비교.
- 새 기술 학습 — 학습 가치와 시행착오 비용을 함께 비교.
- 아직 정하기 어려움 — 두 우선순위에서 결론이 어떻게 달라지는지 먼저 설명.

UI는 직접 입력도 허용한다. 선택 전에 생소한 용어를 쉬운 말로 설명하고, 답을 받은 뒤 어떤 판단이 달라졌는지 한 문장으로 연결한다.

## 필요한 질문을 찾는 관점

| 관점 | 상황으로 묻는 예 |
| --- | --- |
| 허용 지연 | 새 알림이 몇 초 늦어도 괜찮은가 |
| 방향·복구 | 서버가 알리기만 하는가, 놓친 내용은 복구해야 하는가 |
| 자원 | 남은 기간, 익숙한 기술, 운영에 쓸 수 있는 시간은 무엇인가 |
| 환경 | 이미 결정된 호스팅과 변경할 수 없는 제약은 무엇인가 |
| 우선순위 | 완성·비용·학습 중 충돌할 때 무엇을 우선할 것인가 |

전 항목을 설문으로 요구하지 않는다. “설계에 어떤 연쇄 영향이 있나요?”처럼 에이전트가 조사해야 할 내용을 사용자에게 떠넘기지 않는다. 사용자가 모른다고 하면 가정·범위별 조건부 비교를 제공하고, 그것을 확정된 요구로 바꾸지 않는다.
