# Rationale · ADR 작성

이미 정리된 판단을 간결한 개인용 ADR로 기록한다. 명시 호출은 `$rationale-write`, `/rationale-write`는 같은 대화 요청이며 앱 명령 등록을 뜻하지 않는다. 기본 출력은 한국어다.

## 입력과 범위

현재 대화의 결정 질문, 제약과 우선순위, 검토한 후보, 근거·출처, 제안 또는 채택 여부, 감수할 단점, 연쇄 변경, 미확인 사항을 재사용한다. 사용자가 같은 정보를 다시 입력하게 하지 않는다. 필수 연쇄 변경과 조건부·선택적 변경을 구분해 영향과 후속 조치에 압축한다.

이미 선택과 이유를 받은 경우 전체 인터뷰·심층 조사를 다시 시작하지 않는다. 빠진 날짜는 미상으로 표현할 수 있으며, 모든 템플릿 칸을 채우려고 질문하지 않는다. 결정의 의미를 바꿀 공백만 [질문 규칙](../rationale/references/interview.md)에 따라 선택형 UI로 확인한다.

사용자가 비교부터 작성을 함께 요청했고 결정 근거가 아직 없다면 [결정 지원 규칙](../rationale/SKILL.md)의 조사 흐름을 먼저 적용한다. 작성만 요청했는데 선택·근거가 없으면 핵심 누락을 확인하고, 조사를 했다고 꾸미지 않는다. 기술 비교가 완료된 뒤 돌아올 때는 다시 이 분기를 반복하지 않는다.

사용자의 실제 선택이면 Accepted, 에이전트의 조건부 추천이나 미채택 제안이면 Proposed다. “바로 작성해줘”는 파일 작성 허용이며 자동으로 채택을 뜻하지 않는다. 작성 범위가 이미 명확하면 초안을 보여준 뒤 저장 허락을 다시 요구하지 않는다.

플러그인의 연결 파일은 현재 SKILL.md 위치를 기준으로 읽는다. 동일한 실행 주체가 규칙을 이어서 적용하며 별도 에이전트나 스킬 호출 도구를 요구하지 않는다.

## 문서 작성

작성 전에 [개인용 템플릿](../rationale/assets/adr-template.md)을 읽는다. 기존 프로젝트 양식 또는 사용자가 지정한 양식이 있으면 우선한다. 새 개인 ADR의 기본은 다음과 같다.

- 제목 직후 날짜·상태를 Markdown 표로 표시한다. YAML만으로 메타데이터를 감추지 않는다. 작성자·결정권자·공유 대상·팀 역할 필드는 기본으로 넣지 않는다.
- `Reconsideration Conditions`를 독립 항목으로 유지한다. 관찰할 변화와 다시 검토할 판단을 연결한다. 숫자 기준은 실제 요구·측정 또는 명시한 제안에 근거하며 임의의 기준을 합의된 요구처럼 쓰지 않는다.
- 템플릿의 안내문과 빈 대괄호를 완성 문서에 남기지 않는다. 미확인 사실은 구체적으로 적는다. 원형의 영문 제목과 한국어 본문을 기본으로 하고 번역 요청을 따른다.
- Context는 2~3문장, 기준은 핵심만, 각 대안은 짧은 장단점으로 쓴다. 명목상의 페이지 수보다 근거와 단점 보존을 우선한다.
- Confirmation은 실제 검증이나 필요한 확인 계획이 있을 때 쓴다. 실행한 검증과 계획을 구분한다. 조사한 주요 기술 주장에는 해당 위치의 출처 링크를 붙인다. 별도 References 목록은 찾아보기 쉬워질 때만 둔다.
- 상세 조사·실험 기록 또는 여러 날 이어지는 작업에만 근거 노트를 추가하고 ADR에서 연결한다. 전체 대화나 내부 추론을 저장하지 않는다.

## 날짜와 상태

날짜는 결정 또는 제안 날짜다. 기존 결정의 날짜를 알면 보존하고, 사후 기록에서 모르면 `미상 (사후 기록일: YYYY-MM-DD)`처럼 구분한다. 오늘을 과거 결정일로 만들어 내지 않는다. 새 제안 날짜는 실행 환경의 현재 날짜를 사용한다.

기본 상태는 `Proposed`. 사용자가 이미 채택했다고 말했거나 현재 선택 의사가 분명하면 `Accepted`로 기록하고 같은 승인을 다시 요구하지 않는다. `Accepted`는 실험 성공이나 구현 완료를 의미하지 않는다. 실제 사용자 결정을 AI 추천으로 대체하지 않는다. 기존 상태 표기가 있으면 유지한다.

채택된 결정의 의미가 바뀌면 후속 ADR을 만들고 이전 기록에 `Superseded`와 후속 링크를 연결한다. 후속안이 아직 제안이라면 기존 결정을 성급히 대체 처리하지 않는다. 철회되어 유효하지 않지만 대체가 없으면 `Deprecated`, 채택 전 기각은 `Rejected`를 쓸 수 있다. 오탈자·깨진 링크 보수는 기존 문서에서 가능하다.

## 저장과 재개

사용자 경로 → 저장소 ADR 관례 → `docs/decisions/NNNN-short-title.md` 순으로 위치를 정한다. 저장 직전에 기존 파일과 같은 결정의 기록을 확인하고 번호·파일을 덮어쓰지 않는다. 비교만 요청받으면 대화에서 제안하고, 작성·저장 요청이면 해당 범위의 파일을 만든다. 기존 사용자 수정은 보존한다. 재실행은 같은 결정의 초안을 갱신하며 불필요한 새 번호를 만들지 않는다.

재개 시 가정, 근거 확인일, 관련 코드 변경만 점검한다. 과거 선택의 당시 근거와 지금 찾은 근거를 구분한다. 사용자가 면접용 정리를 원하면 실제 기록에서 설명을 추출하고, 미실시 벤치마크·성과·검토 경험을 만들지 않는다.

마지막에는 선택 또는 제안, 결정적 이유, 수용할 단점, 남은 확인과 저장 위치를 짧게 보고한다. 파일 저장과 기술 채택을 혼동하지 않는다.
