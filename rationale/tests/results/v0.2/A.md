현재는 **A 유지**를 조건부로 추천합니다. 2주 기한이 우선이고 약 10초 지연을 허용하므로, 익숙한 REST 조회를 유지하는 편이 새 endpoint와 연결 관리를 도입하는 B보다 일정 위험이 작다는 판단입니다. 이는 제공 자료에서 내린 추론이며, A가 예상 활성 화면 30개를 감당한다는 성능 결론은 아닙니다. 주기적 요청과 지연을 감수해야 하며 최종 채택은 아직 사용자의 선택입니다.

| 기준 | A 유지 | B 도입 |
| --- | --- | --- |
| 2주 기한 | 조건부: 익숙한 방식이므로 유리하나 완료 보장은 없음 | 미확인: endpoint·연결 관리의 추가 작업량 미상 |
| 약 10초 대기 | 조건부: 요청 간격과 처리 시간을 포함해 확인 필요 | 미확인: 전용 스트림이라는 정보만으로 실제 지연을 보장할 수 없음 |
| 직접 요금 | 추가 요금 없음 | 월 고정 5단위 |
| 개발·운영 부담 | 기존 조회 유지, 주기적 요청 부담 | 전용 endpoint 및 연결 관리 필요 |
| 예상 화면 30개 성능 | 미확인 | 미확인 |

비용은 사용자가 제공한 가상 문서 요약의 값입니다. 통화·요금 적용 시점·포함 사용량·전송 비용·개발 및 운영 인건비는 미확인이므로 총비용으로 해석할 수 없습니다. A의 추가 요금 없음도 운영 비용이 전혀 없다는 뜻은 아닙니다.

중요한 설계·연쇄 영향은 다음과 같습니다.

- **A — 필수 확인:** 주기적 조회 → 요청 빈도와 화면 표시 지연 → 간격·처리 시간을 함께 확인하고 조정. 약 10초 대기를 맞춰야 하는 현재 조건에 해당하며, 제공 정보만으로 새 구현이 반드시 필요하다고 단정하지 않습니다.
- **B — 필수 변경:** 전용 스트림 도입 → 서버 endpoint와 수신 측 연동 → endpoint 구현·연동 및 전용 연결 관리. 연결 종료·재연결 상황을 어떻게 처리할지도 설계해야 한다는 추론입니다. 구체적인 복구 보장은 자료에 없습니다.
- **B — 조건부 변경:** 여러 서버 분산 배포 → 서버 간 전달 구성 → 공유 전달 구성 도입. 현재는 서버 한 대이므로 현재 필수 구성에 넣지 않습니다.
- **선택적 개선:** 추후 전환 부담을 줄이려는 경우 → 화면의 표시 처리와 수신 방식의 결합 → 두 부분 분리 검토. 현재 요구 충족의 전제는 아니며, 2주 일정에 부담이면 미룰 수 있습니다.

B의 가장 강한 반론은 A의 반복 조회와 대기 문제를 줄일 가능성입니다. 다만 해당 효과의 크기와 30개 화면에서의 성능은 제공 자료로 확인되지 않았습니다. 허용 지연이 더 짧아지거나 A의 요청 부담이 실제로 문제가 되면 B를 다시 비교할 이유가 생깁니다.

결론을 바꿀 가장 작은 검증은 **서버 한 대에서 예상 활성 화면 30개를 재현하고, A의 변경 발생부터 표시까지 지연과 요청 처리 부담을 함께 측정하는 것**입니다. 이는 미실시 계획이며, 요청 간격을 10초로 두면 처리 시간까지 포함한 지연이 10초 안에 든다고 가정해서는 안 됩니다. 측정 결과가 허용 지연에 맞지 않으면 간격 조정 비용과 B 도입 비용을 다시 비교하면 됩니다.

근거는 사용자 제공 가상 문서 요약과 요구뿐입니다. 실제 문서 원문·코드·웹·성능 측정을 확인하지 않았고 최신성도 미확인입니다. 결정 지원 범위에서 마치며 ADR은 생성하지 않았습니다.
