# ADR-0001: 개인 프로젝트 알림에 10초 폴링 채택

| 속성 | 값 |
| --- | --- |
| 날짜 | 미상 (사후 기록일: 2026-09-19) |
| 상태 | Accepted |

## Context and Problem Statement

개인 프로젝트에 알림을 추가하며 기존 REST API와 알림 DB를 활용할 수 있다. 새 기술 학습보다 2주 내 완성이 우선이고, 활성 화면 약 30개는 사용자 예상이며 성능 테스트는 아직 하지 않았다.

## Decision Drivers

- 2주 내 완성을 새 기술 학습보다 우선한다.
- 기존 REST API와 알림 DB를 활용한다.
- 현재 장기 연결 운영을 추가하고 싶지 않다.
- 지속적인 양방향 통신 요구가 없다.

## Considered Options

### 10초 폴링

- 장점: 기존 REST API와 알림 DB를 활용하는 선택이다.
- 단점: 다음 조회까지 알림 표시가 지연될 수 있으며, 반복 조회의 실제 부하는 확인하지 않았다.

### SSE

- 장점: 서버에서 보내는 알림을 받는 방식으로 검토한 후보다.
- 단점: 사용자가 지금 추가하고 싶지 않은 장기 연결 운영이 필요해 보류했다.

### WebSocket

- 장점: 지속적인 양방향 통신이 필요한 경우 활용할 수 있는 후보다.
- 단점: 현재 지속 양방향 요구가 없어 선택할 근거가 부족하다.

## Decision Outcome

**알림을 10초 주기로 폴링하기로 결정했다.**

기존 구성을 활용하고 2주 내 완성을 우선한다. 가까운 대안인 SSE는 현재 추가하고 싶지 않은 장기 연결 운영 때문에 보류했고, WebSocket은 지속적인 양방향 요구가 없어 선택하지 않았다.

## Consequences

- 긍정적 영향: 기존 API와 DB를 활용하고 장기 연결 운영의 추가를 미룬다.
- 감수할 단점: 조회 사이의 알림 표시 지연과 반복 요청이 발생한다. 10초 주기 채택은 실제 지연 만족도나 성능의 검증 완료를 뜻하지 않는다.

## Confirmation

- 현재 확인된 상태: 성능 테스트와 실험은 아직 하지 않았다. 활성 화면 약 30개는 측정값이 아닌 사용자 예상이다.
- 확인 제안: 예상 규모에서 폴링 요청의 응답 시간·오류·서버 및 DB 부하와 실제 알림 표시 지연을 확인한다. 이 확인은 실행 결과가 아닌 제안이다.
- 미정 사항: 허용 성능과 지연의 수치 기준은 아직 제공되지 않았다.

## Reconsideration Conditions

- 실제 사용에서 알림 표시 지연이 요구를 충족하지 못하면 조회 주기와 SSE를 다시 검토한다.
- 실제 활성 화면 수 또는 부하가 예상과 달라 반복 조회 부담이 문제가 되면 폴링 방식과 대안을 재검토한다. 판단할 성능 기준은 확인이 필요하다.
- 지속적인 양방향 통신 요구가 생기면 WebSocket을 다시 검토한다.
- 장기 연결 운영을 감당할 여건이 달라지면 SSE 보류 판단을 다시 검토한다.
