# Team Start

Codex 앱에서 `$team-start`로 호출한다. GitHub에 익숙하지 않은 팀장의 설명을 받아 새 협업 공간을 준비한다. 팀원에게는 이 스킬이 필요 없다. 계획, 생성·이어가기, 점검을 자연어로 구분한다.

## 대화

1. 목적·기간·팀 규모·이미 결정한 내용을 추출한다. 필요한 선택만 짧게 설명하고 추천한다. 기존 답변과 생성·초대 허락을 반복해서 묻지 않는다.
2. `gh` 로그인과 사용할 소유자·권한을 읽기로 확인한다. 적합한 기존 조직을 제안하되 강제하지 않는다. 개인 소유와 조직의 차이, 새 조직 생성, 권한 제약이 필요할 때만 [github.md](references/github.md)를 읽는다.
3. **소유자, 저장소명, 공개 여부, 새 프로젝트의 절대 경로, 초대할 GitHub 로그인**, 보드·AI 안내 사용 여부를 정한다. 현재 작업 폴더를 새 프로젝트로 간주하거나 업로드하지 않는다. 임시 폴더 대신 사용자의 지속적인 프로젝트 보관 위치를 사용한다.
4. 무료·비공개를 우선 추천한다. 해커톤은 PR 기록과 승인 0명, 지속 협업은 다른 팀원 승인 1명을 추천한다. 중요 미정 사항은 답을 받은 뒤 적용한다. 담당자·커밋 문체·스타일·라이선스를 임의로 정하지 않는다.
5. 생성 자원, 저장소·보드의 팀원별 쓰기 권한, 문서 초안, 강제 가능한 규칙과 보류 항목을 보여준다. 실제 저장소 API로 기능 지원을 확인하며 요금제 정보가 없다는 이유로 추가 인증을 요구하지 않는다.

새 저장소 하나와 2~10명 팀에 집중한다. 앱 개발·배포·결제·조직 전체 정책 변경·기존 저장소 전환은 범위 밖이다. 새 조직은 공식 웹 화면에서 사용자가 생성한 뒤 이어간다. 미지정 상대 초대나 공개 전환을 추정해서 실행하지 않는다.

## 실행

[interface.md](references/interface.md)에서 입력·출력을 확인한다. macOS Codex 앱에서 검증했으며 도우미는 Python 3.9+, git, 인증된 gh와 POSIX 파일 잠금을 사용한다. 인증 토큰을 대화·파일·명령 인자에 복사하지 않는다.

- **계획:** spec을 별도 산출물로 작성하고 `plan --spec …`으로 문서 초안을 확인한다. `--offline`은 계정 확인 없는 미리보기다.
- **생성·이어가기:** 허용된 설정으로 `apply --spec …` 또는 `apply --path …`를 실행한다.
- **점검:** `check --path …`로 읽기만 수행한다. 점검 요청을 복구 허락으로 해석하지 않는다.

실패 원인을 해결한 뒤 같은 프로젝트에서 재개한다. `.team-start`의 기록을 삭제·수정해 충돌 방지를 우회하지 않는다. 사용자 변경은 보류로 보고하며 차이를 설명한다. 이 도구 밖의 수동 수정은 별도 요청 범위에서 처리한다.

설정 PR을 생성하거나 요청에 따라 이어서 작업했다면 반환된 `setup_pr.url`을 Codex의 PR 첨부 도구로 현재 작업에 첨부한다. 자동 병합하지 않는다.

## 완료 판단

- README는 시작점, CONTRIBUTING은 선택한 협업 흐름, 선택적 AGENTS는 확인된 명령과 안내 링크다. 미정은 표시하고 CODEOWNERS는 자동 생성하지 않는다.
- 초대 발송과 참여 완료를 구분한다. 검토자가 부족하면 새 승인 요건은 보류하고 기존 요건은 완화하지 않는다.
- 보드와 저장소 접근은 별개다. 공개 GraphQL은 보드 협업자 역할을 재조회할 수 없으므로, **권한 변경 응답만으로 접근 확인을 주장하지 않는다.** 가능한 브라우저 도구로 Settings > Manage access의 실제 로그인·역할을 확인하고 근거를 남긴다. 불가능하면 설정 링크와 수동 확인 항목을 남긴다. 보드의 Status 분류도 UI가 가능하면 확인한다.
- 코드가 없으면 CI는 보류한다. 코드가 생기면 실제 설치·검사 명령을 실행해 확인한 뒤 interface.md의 CI 입력을 작성한다. 가짜 성공 명령은 사용하지 않는다. 외부 action은 공식 출처에서 확인한 전체 SHA를 쓰며 기존 워크플로·검사 이름 충돌을 확인한다.
- 보호된 main의 파일 변경은 PR로 제안한다. 병합 후 해당 main의 CI 성공과 출처를 확인해야 필수 검사를 연결한다. 보호 규칙을 끄거나 우회하지 않는다.

## 전달

저장소·보드·설정 PR 링크, 적용 확인 / 초대 수락 대기 / 보류 / 지원되지 않음 / 실패와 각 다음 행동을 안내한다. exit 0도 모든 기능 완성을 뜻하지 않는다. 팀원의 첫 행동은 초대 수락 → 저장소·보드 접근 확인 → clone → 이슈 → 작업 브랜치 → PR이다. 별도 요청 없이 이메일·메신저를 발송하지 않는다.
